# 消息变更与缓存恢复契约补充提案

2026-09-09；状态：**PROPOSED / 未批准实施**。来源：[MX-A07B-1](../tasks/active/MX-A07B-1.md)。本阶段 **BLOCKED_BY_CONTRACT**，只提交复现、回归输入与提案；没有改变 v1 schema、事件、序列、数据库或运行时代码。

## 1. 已复现的 v1 行为

独立当前源码 Spring JAR + MySQL 8.4 + Redis 7.4，HTTP/WS 地址 `127.0.0.1:18401`。完整受控步骤和原始输出见 [报告](../reports/仓库审查/MX-A07B-1_消息变更与缓存一致性复现_2026-09-09.md)。所有正文/账号均为专用测试数据。

1. 发送 A(sequence=1)、B(sequence=2，isBurn=1) 和 60 条后续消息；接收端缓存至 62 并断开真实 socket。
2. 服务端通过真实 `CHAT_RECALL` / `CHAT_BURN` 修改 A/B。出站事件仍带原 sequence 1/2；正文在数据库查询结果中已清空。
3. 接收端重新 AUTH，`SYNC_REQUEST.positions={conversation:62}` 返回 `messages=[]`、`latestPositions=62`、`hasMore=false`。最近 50 条 history 也没有 A/B。
4. 从 0 重放可读到 A 的 `isRecalled=1` 与 B 的 `status=2`，两者正文为空。
5. 进一步使用**实际 Dart ChatController、MeshXApi、RealtimeConnection、FileChatStore**：缓存新消息 63/64 至游标124→pause→真实 REST 撤回/焚毁→resume→select 的最近历史→新控制器从磁盘 restore。服务端正文为空，客户端仍保存和显示旧正文，游标124不变。

因此已证实的是：**当前增量消息 sequence 不提供旧消息变更的最终恢复能力**。不是仅阅读 `.gt(sequence, after)` 后推断。

`CHAT_READ` 是阅读者自己的会话读位点，不是普通消息对端已读证明。离线阅读者可从 `GET /chat/conversations` 恢复 `lastReadSequence`；真实测试位点62，PASS。

移出群后：列表不再包含群，显式请求旧会话 SYNC 得到 `deniedConversationIds`，history业务code400，CHAT_SEND得到ERROR。现有服务端权限路径可用，不需要新事件才能拒绝访问。

删除好友后：**仍允许参与者读取旧私聊历史和SYNC，发送被拒绝**。这是当前 `canAccess` 与 `canSend` 的区别，不能把好友删除自动解释为历史阅读授权也被撤销。改变此产品权限语义须单独批准。

## 2. 缺口分类与安全影响

| 场景 | 分类 | 当前影响 |
|---|---|---|
| 离线后恢复旧撤回/焚毁 | PROTOCOL_GAP；安全FAIL | Web/Flutter增量游标均可能永久保留旧正文；最近窗口补查不能覆盖全部旧缓存 |
| Flutter实时RECALL/BURN/READ/REMOVED | CLIENT_GAP | 控制器没有这些分支；仅刷新Widget不能解决磁盘重现 |
| 群从摘要消失 | CLIENT_GAP | Flutter只同步新摘要中的会话，跳过旧群的denied路径；旧active、正文、cursor和queued消息仍在磁盘 |
| 显式denied响应 | 现有能力PASS，需正确接入 | Flutter分支会移除消息（其中包含outbox）、游标、列表、active；正常摘要消失流程没有经过它 |
| Web后台会话收到BURN | CLIENT_GAP | 当前handler找不到内存target时不清该条缓存；当前已打开消息可清空并保存 |
| Web收到REMOVED | CLIENT_GAP（持久清理） | 当前UI/访问集合/运行游标清除，底层消息缓存仍保留；不等于重启持久删除 |
| 未识别的受限制消息status | CLIENT_GAP | Dart丢弃status/isBurn，可能按普通文本显示并持久化 |
| 任意未知事件 | 兼容性约束 | v1要求忽略未知非致命事件，不能擅自将一切扩展事件定义为删除命令；需协商安全状态能力 |

这不承诺撤回已复制、截屏、导出或被不可信客户端持有的内容。安全目标是**受支持客户端在成功恢复后不继续由自己的缓存展示/发送被限制内容**，不是远程抹除保证。

## 3. 现有 v1 的备选：全量缓存重建

从0重放保留行的撤回/焚毁状态已经真实验证为PASS。可评审的无schema方案是：在重新开放会话前隔离旧缓存，使用权威可访问目录并清除已失权会话，完整分页重建消息，再开放展示和发送；本地outbox单独按权限处理。

本轮没有实施，也没有证明“所有v1方案在数学上都不可行”。该方案有明确代价与未决点：

- 必须清旧缓存再建立新快照，不能普通merge，否则物理删除/缺失消息仍残留；失败时不能回退到受限制旧正文。
- v1没有快照token/变更高水位。分页期间已读过的页发生变更、REST变更没有实时通知、删除/保留期限、群权限中途改变，需要额外的持续重查和阻断规则，不能凭本轮单次全量成功证明有界恢复保证。
- 每次重连全量拉取会改变A05离线可用性、流量和延迟；必须给出允许展示的缓存状态、历史上限和失败策略。只拉最近50/200条不构成这个方案。
- 好友删除不等于禁止读历史；仅凭摘要缺失无法推导所有产品权限。发送授权需要单独的权威判断。

用户授权要求发现契约缺口后停止扩大实现，因此这项备选与增量补充一起提交评审。可选择一个独立受控任务验证全量重建，也可批准下述增量补充；本卡不会悄悄将v1改为另一种sequence语义。

## 4. 建议的增量补充（字段/事件名均待评审）

### 两套互不替代的位点

- 现有 `message.sequence`、CHAT_ACK与`SYNC_REQUEST.positions`原义不变，继续排序/补齐新增消息。
- 新增独立的持久**变更日志位点**，不要用原消息sequence兼任。建议按用户可见范围恢复：日志条目含稳定eventId、mutation cursor、conversationId、messageId（适用时）、受控状态/版本；权限撤销通知应能在被移除后仍交付给原接收者，但不夹带群内新内容/成员隐私。
- 可选能力协商必须在恢复前明确。新增端点或显式协商后的扩展消息由后续任务定名；本提案不生成或接受schema基线。旧服务器不支持时，新客户端不得把“没有事件”理解为“已安全恢复”。
- 状态至少区分普通、撤回、焚毁、不可用，以及可读/可发/移除。物理删除必须有可恢复tombstone或强制全量重建指示，不能靠缺行猜测。

### 快照与日志衔接

1. 认证后取得与账号/节点绑定的快照边界H及目录/权限版本。先建立受限制内容不可见的恢复状态。
2. 在该边界下分页取快照；实现可以用一致快照token，或证明“在快照前取H，随后重放H之后全部变更”的方案不会丢失删除/授权变更。必须测试变更发生于分页之间的竞态。
3. 顺序补拉变更，完整应用并原子持久化后才保存变更游标并标记恢复完成。分页有明确hasMore与前进保证；重复安全，跨页不能跳过。
4. 游标过期/日志压缩必须明确要求重建；客户端清掉受影响旧缓存，不能直接将游标跳至latest并继续显示旧正文。离线保留上限、日志保留时间由部署/产品一并批准。
5. 在线推送仅加速，持久日志是恢复依据；HTTP与WS触发的所有变更走同一事务/日志路径。

### Java职责与权限

业务状态更新、变更记录及需要的派发outbox须位于同一事务边界，提交后再通知。已撤回正文不写进变更日志。重复撤回/焚毁、失败事务、并发移除与发送分别测试；每页重查当前用户权限。跨实例路由依赖现有共享数据库/Redis，不引入独立节点复制。

已读是独立私有游标：只同步阅读者自己的设备；不得通过新日志向其他普通用户广播私有阅读信息。最后可读位置与普通ACK不可互相替代。

## 5. 客户端实施边界（后续任务）

### Dart Core与持久化

状态转换放纯Dart Core，名称可采用 `MessageMutationPolicy / ReadStatePolicy / ConversationAccessState`。不引入Widget、MethodChannel、平台通知或数据库实例。

同一owner的状态以 `origin + userId + connection generation + conversation ownership` 校验后处理。一个持久化提交覆盖：消息正文清理/tombstone、会话状态、outbox处置、旧通知路由失效与两个游标；保存失败不能仅内存显示成功。重启恢复不得把旧普通正文覆盖更高版本tombstone。

建议撤回/焚毁对同消息普通快照具有单调优先级：重复无副作用；先变更后原消息不复活；迟到原消息/低版本快照不能降级。未知**已协商安全状态**进入unavailable并请求权威恢复；未知无关事件继续遵守兼容规则。缓存格式升级要显式处理旧版缺失status/isBurn的记录。

### 权限与outbox

- “会话被移除/禁止阅读”：移除目录和active，清正文、预览、对应文件引用/通知路由，清或墓碑化该会话游标；pending outbox默认**丢弃正文并保留不含正文的失败原因**。不自动重试。
- “仅禁止发送但仍可读”：只保留允许读的历史；outbox转不可自动发送状态。若保留草稿需显式产品授权与用户操作，不能重连或重新加群后自动复活旧队列。
- 恢复发送前必须有当前权限判断，不能先发敏感正文再等403。版本/权限变化后再校验；真实服务端仍为最终裁决者。
- 本轮Flutter已证明显式denied可清队列，但摘要消失路径缺失；Web保留待处理outbox不能等价为已完成安全清理。两端具体保留策略需统一。

### markRead规则

ACK只称已发送；不添加未经服务端证明的peer read状态。建议只在**前台、当前账号、当前可访问会话、消息实际进入可见范围**后提交读位点；位点需与收到的连续消息/可见规则一致，不能因缓存中存在更高sequence直接读到最高。

打开会话触发可见性评估，不无条件读整段history。切换会话/后台停止获取新的阅读位置；重连先补状态，再对当前可见内容评估。已经在前台实际读过而等待联网的私有读位点可以延迟发送，但重新检查账号与权限。historical SYNC本身不是阅读动作。Web现有规则能检查当前会话/前台/页面可见，但按传入集合最大sequence，不是逐条viewport证明；Flutter当前完全不发CHAT_READ。须分别补验，不能把sent写成read。

### 通知

RECALL/BURN/REMOVED应取消对应待发通知/路由，并禁止后续旧正文投递产生新通知；状态修正和历史补同步不视为新消息。通知适配器仍在应用层。A06 policy只接收live/own/duplicate/viewing等布尔条件，没有安全状态输入；需要增加状态层的资格检查，不以generic通知正文代替资格校验。本轮真实Dart补同步观察到0通知，仅证明该次历史恢复静默。完整点击仍留后续阶段。

| 老Web/Tauri/Flutter | 仍可按原v1通信，但**不会自动得到旧变更安全保证**；不能只增加可选字段便称旧客户端修复 |
| 老服务端+新客户端 | 检测不支持，使用经批准且验证的全量重建兼容模式，或明确不可安全恢复并阻断相关能力；不伪装已同步 |

若组织要求安全恢复为强制门禁，须明确最低客户端能力及拒绝/升级提示策略；不能悄悄改变登录或设备身份。R04/v2身份治理不在本提案实施范围。

## 7. migration / rollback

先批准契约、共享向量、日志保留和老客户端策略，再做**加法数据库迁移**与双路径运行；不自动执行SQL。服务端先提供能力并核验真实事务日志，再发布Web/Dart客户端消费。已有消息sequence永不回填为mutation cursor。

首次客户端升级处理旧缓存版本：受保护正文隔离、持久化迁移可恢复、不覆盖凭据或换应用ID；新旧格式不得互相误读。测试升级失败/磁盘满/中断与重新启动。

回滚可关闭新能力派发，但保留日志和新列以便恢复，不破坏旧消息顺序。已经依赖新能力的客户端遇到降级必须重新建立安全恢复边界，不能恢复显示已清除正文。数据库破坏性回滚和删日志不作为紧急开关；旧客户端行为风险单独记录。

## 8. test vectors与批准后验收

现有 [7项共享复现向量](../../contracts/test-vectors/message-mutation-v1.json) 由实际TS handlers/连接和Dart controller读取。它们标明安全目标，**没有把已知错误当作允许发布的兼容基线**。本轮回归断言的是当前观测，未来修复时应以正式批准的安全期望替换这些characterization断言，保留原始复现输出。

批准后至少新增：重复mutation；先mutation后original；旧快照晚到；重连mutation；旧账号/节点/连接事件；未知安全状态；会话移除；权限变更与pending outbox；恢复失败不泄露；真实文件重启；读位点可见/未打开/后台/切换/重连/history；通知状态修正静默。

服务端还必须覆盖：事务回滚无日志/ACK、双实例派发、并发mutation版本、分页中发生撤回、删除尾部、日志压缩/过期、非成员及已移除接收者的最小失效通知、旧新客户端组合。最终跑真实Server→Web和Server→Flutter缓存→断网→变更→恢复→重启；不能仅用reducer过门禁。

批准前保持G03/G00等相关首发门禁未关闭。A07B-2好友/搜索可作为独立开发切片另行授权，但不得因此声称安全接收或Release Ready；本轮不启动。
